# دموی قابل تکرار اثر نسخه بر قیمت جاری

این راهنما سناریوی V1 جاری، V2 ردشده و V3 آماده بررسی را از مسیر عادی رابط و API
اجرا می‌کند. هیچ pointer یا داده‌ای مستقیم در دیتابیس تغییر داده نمی‌شود.

## پیش‌نیاز و اجرای محیط

- Docker Desktop یا Docker Engine در حال اجرا باشد.
- Node، pnpm و Python پروژه طبق README نصب شده باشند.
- اگر `.env` ندارید، یک‌بار `cp .env.example .env` را اجرا کنید. فایل موجود را
  بازنویسی نکنید.

از ریشه مخزن:

```bash
make compose-up
```

این فرمان PostgreSQL و MinIO را بالا می‌آورد، bucket خصوصی را آماده می‌کند، migration
را اجرا می‌کند و backend/frontend را راه می‌اندازد. وضعیت را با این دو نشانی بررسی
کنید:

- رابط: `http://localhost:3000`
- readiness: `http://localhost:8000/health/ready`

readiness باید HTTP 200 و status برابر `ok` بدهد. اگر MinIO آماده نباشد، upload با
`503 OBJECT_STORAGE_UNAVAILABLE` متوقف می‌شود؛ نسخه یا قیمت ناقص ساخته نمی‌شود.

## فایل‌های دمو

- `fixtures/demo/current-price-impact/current-price-impact-v1.xlsx`
- `fixtures/demo/current-price-impact/current-price-impact-v2.xlsx`
- `fixtures/demo/current-price-impact/current-price-impact-v3.xlsx`

هر فایل یک worksheet بدون macro و formula دارد. کد `0001` متن است و صفرهای ابتدایی
آن باید در جدول کالاها و تغییرات حفظ شوند. همه قیمت‌ها عدد صحیح ریال‌اند.

## مرحله ۱: ساخت تأمین‌کننده جدا

1. با نقش OWNER وارد شوید. در development می‌توانید از `/register` حساب تازه بسازید.
2. به `/suppliers/new` بروید.
3. نام یکتا مانند «تأمین‌کننده آزمایشی اثر قیمت ۱۴۰۵۰۷۲۲» وارد کنید.
4. پس از ساخت، صفحه جزئیات همان Supplier را باز نگه دارید.

برای اجرای دوباره دمو Supplier تازه با نام یکتا بسازید تا dedup فایل همان Supplier
مانع upload تکراری نشود.

## مرحله ۲: V1 و حالت NO_CURRENT

1. از صفحه Supplier، بارگذاری فایل قیمت را باز کنید.
2. فایل V1 را انتخاب و upload کنید.
3. Import موفق باید ۲ ردیف معتبر نشان دهد: `0001` با قیمت ۱۰۰٬۰۰۰ ریال و
   `SW-001` با قیمت ۲۰۰٬۰۰۰ ریال.
4. checkbox ساخت Version تغییرناپذیر را بزنید و Version 1 را بسازید.
5. در صفحه Version 1، بخش «اثر این نسخه بر قیمت جاری» باید پیام زیر را نشان دهد:
   «هنوز قیمت جاری تأییدشده‌ای وجود ندارد؛ این نسخه در صورت تأیید، اولین قیمت جاری
   خواهد شد.»
6. summary و جدول تغییر ساختگی نباید نمایش داده شوند؛ جدول مستقل کالاهای Version
   همچنان دو ردیف را دارد.
7. confirmation Approval را بزنید و Version 1 را تأیید کنید.

نتیجه: کارت قیمت جاری Supplier باید Version 1 را نشان دهد و Audit یک رویداد Approval
داشته باشد.

## مرحله ۳: V2 و رد نسخه

1. فایل V2 را برای همان Supplier upload و Version 2 را بسازید.
2. گزارش تاریخی V2 نسبت به V1 یک افزایش قیمت برای `0001` از ۱۰۰٬۰۰۰ به ۱۲۰٬۰۰۰
   ریال نشان می‌دهد.
3. «رد نسخه» را باز کنید، دلیل «این فایل تأیید نمی‌شود» را وارد کنید، confirmation
   رد را بزنید و تصمیم را ثبت کنید.

نتیجه: Version 2 باید Rejected باشد و کارت قیمت جاری همچنان Version 1 را نشان دهد.

## مرحله ۴: V3 و تفاوت دو مبنا

1. فایل V3 را upload و Version 3 را بسازید.
2. صفحه Version 3 را باز کنید.
3. بخش «تغییرات نسبت به نسخه قبلی ثبت‌شده» باید مبنای تاریخی Version 2 را نشان دهد.
4. بخش «اثر این نسخه بر قیمت جاری» باید مبنای عملیاتی Version 1 را نشان دهد.

نتیجه عددی مورد انتظار:

| گزارش | added | removed | price_changed | metadata_only_changed | unchanged |
| --- | ---: | ---: | ---: | ---: | ---: |
| V3 نسبت به V1 جاری | 1 | 1 | 1 | 0 | 0 |
| V3 نسبت به V2 تاریخی | 1 | 1 | 0 | 1 | 0 |

در گزارش جاری، `0001` باید هم‌زمان برچسب «تغییر قیمت» و «تغییر تعداد در بسته» داشته
باشد: قیمت ۲۰٪ افزایش یافته و تعداد بسته از ۱۰۰ به ۵۰ رسیده است. در گزارش تاریخی،
همین کد فقط تغییر بسته‌بندی دارد. از مبلغ بسته درباره ارزان یا گران‌شدن هر عدد
نتیجه‌گیری نکنید؛ چنین قاعده‌ای در دامنه تعریف نشده است.

فیلتر «قیمت» گزارش جاری فقط `0001` را نشان می‌دهد. فیلتر «بسته‌بندی» نیز `0001`
را نشان می‌دهد. تغییر فیلتر جاری نباید فیلتر گزارش تاریخی را عوض کند.

## مرحله ۵: تأیید V3

1. پس از دیدن مبنای جاری Version 1، confirmation Approval را بزنید.
2. Version 3 را تأیید کنید.
3. صفحه Supplier را refresh کنید.

نتیجه: Current باید Version 3 باشد؛ Version 1 به‌عنوان Version تأییدشده تاریخی حفظ
شود؛ Version 2 ردشده باقی بماند و Audit رویداد Approval V3 را با actor/time نشان دهد.
پس از terminalشدن V3، گزارش زنده current-impact دیگر به‌عنوان شاهد تاریخی نمایش
داده نمی‌شود؛ گزارش تاریخی و Audit باقی می‌مانند.

## نقش OPERATOR

اگر حساب OPERATOR از قبل دارید، همین صفحات را با آن باز کنید. هر دو گزارش و Audit
قابل مشاهده‌اند، اما دکمه Approval/Reject وجود ندارد. چون قابلیت دعوت عضو هنوز
پیاده نشده است، برای دمو endpoint یا credential جعلی نسازید. کنترل این نقش با تست
یکپارچه موجود نیز قابل تکرار است:

```bash
cd backend
uv run pytest tests/integration/test_price_list_approval_api.py -q
```

## سناریوی stale با دو نشست OWNER

1. پیش از تأیید V3، صفحه آن را در دو مرورگر یا یک پنجره عادی و ناشناس با همان OWNER
   باز کنید.
2. در هر دو نشست گزارش pin‌شده به Version 1 را ببینید و confirmation را بزنید.
3. در نشست اول V3 را تأیید کنید.
4. در نشست دوم تلاش به تصمیم را انجام دهید.

نشست دوم نباید تصمیم دوم ثبت کند. ممکن است UI ابتدا وضعیت terminal تازه را دریافت و
دکمه را مسدود کند، یا Backend پاسخ 409 بدهد. در هر دو حالت confirmation قبلی پاک و
اطلاعات تازه دریافت می‌شود؛ mutation خودکار تکرار نمی‌شود.

## آزمون خطای MinIO و بازیابی

برای آزمون کنترل‌شده 503 روی داده دموی تازه:

```bash
docker compose stop minio
```

یک upload تازه را امتحان کنید. باید پیام در دسترس نبودن فضای نگهداری و HTTP 503
بگیرید؛ Import/Version ناقص نباید ساخته شود. سپس MinIO را بازیابی کنید:

```bash
docker compose up -d minio
docker compose run --rm minio-init
```

readiness را دوباره بررسی و upload را با اقدام صریح خودتان تکرار کنید. اگر 503 باقی
ماند، `docker compose ps` و log سرویس MinIO را بررسی کنید؛ retry خودکار upload وجود
ندارد.

## محدودیت معنایی

این دمو ثابت می‌کند تصمیم داخلی بر snapshot جاری درست و قابل ممیزی است. تأیید داخلی
یا مقایسه Versionها ثابت نمی‌کند قیمت تأمین‌کننده امروز در بازار تازه است یا موجودی
لحظه‌ای دارد.
