# سند اسپرینت‌های محصول و یادگیری قیمت‌یار

آخرین به‌روزرسانی: 2026-08-30

## هدف سند

این سند مسیر اجرایی قیمت‌یار را از وضعیت فعلی تا محصول قابل فروش مشخص می‌کند. هدف این نیست که همه امکانات از ابتدا ساخته شوند؛ هدف این است که هر اسپرینت یک مشکل واقعی از عمده‌فروش‌های تجهیزات شبکه و دوربین مداربسته تهران را حل کند، یک خروجی قابل تست داشته باشد، و هم‌زمان مفاهیم اصلی معماری بک‌اند، فرانت‌اند، داده و AI به‌صورت عملی یاد گرفته شوند.

## تعریف محصول

قیمت‌یار یک وب‌اپ B2B، فارسی، RTL و Desktop-first برای عمده‌فروش‌های تجهیزات شبکه و دوربین مداربسته تهران است. کار اصلی محصول این است که فایل‌های قیمت تأمین‌کنندگان را به داده قابل اعتماد تبدیل کند، تغییرات قیمت و اطلاعات کالا را نشان دهد، نسخه معتبر قیمت را با تأیید انسانی نگه دارد، و در مراحل بعدی بر اساس همان قیمت معتبر، قیمت فروش، پیش‌فاکتور و پیگیری را مدیریت کند.

در وضعیت فعلی، محصول نباید خودش قیمت را تأیید کند، پیش‌فاکتور را بدون اجازه ارسال کند، یا خروجی AI را حقیقت قطعی فرض کند. انسان همیشه نقطه تأیید نهایی است.

## مخاطب هدف شروع

- صنف شروع: عمده‌فروش‌های تجهیزات شبکه و دوربین مداربسته
- جغرافیا: تهران
- کاربر اصلی: مالک، مدیر فروش، اپراتور قیمت
- اندازه مشتری اولیه: ۲ تا ۲۰ کاربر و ۵۰۰ تا ۲۰٬۰۰۰ قلم کالا
- درد اصلی: تغییر مداوم قیمت تأمین‌کننده، خطای دستی در مقایسه فایل‌ها، فروش با قیمت قدیمی، و اتلاف وقت در ساخت پیش‌فاکتور

این بازار برای شروع مناسب است چون کالاها کددارند، تغییر قیمت زیاد است، فایل Excel رایج است، حاشیه سود حساس است، و خطای قیمت مستقیماً به ضرر مالی تبدیل می‌شود.

## اصل مسیر محصول

قیمت‌یار باید از یک مشکل باریک و پرتکرار شروع کند:

> وقتی تأمین‌کننده فایل قیمت جدید می‌فرستد، کاربر بتواند در چند دقیقه بفهمد چه کالاهایی تغییر کرده‌اند و بعد از بازبینی، نسخه درست را مبنای فروش کند.

بعد از حل قابل اعتماد این مسئله، محصول به‌ترتیب به سمت ذخیره نسخه‌ها، تأیید، قیمت‌گذاری مشتری، پیش‌فاکتور، هشدار قیمت منقضی‌شده، PDF و تصویر حرکت می‌کند.

## قواعد ثابت همه اسپرینت‌ها

- پول canonical همیشه ریال ایران و عدد صحیح است.
- تومان فقط در آینده می‌تواند ورودی/نمایش کنترل‌شده باشد؛ در جریان فعلی نباید وارد مدل دامنه شود.
- فایل، متن Excel، PDF، تصویر و خروجی AI همیشه untrusted هستند.
- داده هر سازمان فقط با session و membership همان سازمان قابل دسترسی است.
- `organization_id` ارسالی از client هیچ‌وقت مجوز دسترسی نیست.
- نسخه تأییدشده قیمت immutable است و update مستقیم نمی‌شود.
- هر تغییر مهم باید تست، مستندات و در صورت نیاز ADR داشته باشد.
- AI در استخراج Excel ساختاریافته استفاده نمی‌شود.
- AI در مراحل PDF/تصویر فقط پیشنهاد ساختاریافته می‌دهد؛ تأیید انسانی اجباری است.

## تعریف Done برای هر اسپرینت

هر اسپرینت فقط وقتی تمام‌شده محسوب می‌شود که:

- رفتار موجود بدون دلیل محصولی شکسته نشده باشد.

## نقشه اسپرینت‌ها

طول پیشنهادی هر اسپرینت برای اجرای تک‌نفره همراه یادگیری، ۱ تا ۲ هفته است. اگر هدف فقط ساخت سریع MVP باشد، بعضی اسپرینت‌ها می‌توانند کوتاه‌تر شوند؛ اما ترتیب وابستگی‌ها بهتر است حفظ شود.

## Sprint 0 — تثبیت foundation فعلی

وضعیت: تقریباً انجام‌شده؛ قبل از ادامه محصول باید فقط بازبینی شود.

هدف:
اطمینان از اینکه پایه فعلی محصول سالم، قابل اجرا و قابل توسعه است.

مشکل کاربر که حل می‌شود:
کاربر می‌تواند وارد حساب شود و دو فایل Excel قیمت را بدون ترمینال مقایسه کند.

چرا اولویت دارد:
اگر همین برش پایه قابل اعتماد نباشد، اضافه‌کردن persistence، پیش‌فاکتور یا AI فقط پیچیدگی روی پایه ناپایدار ایجاد می‌کند.

خروجی محصول:

- ثبت‌نام/ورود امن
- داشبورد مقایسه دو فایل XLSX
- نمایش تغییرات قیمت و تغییرات پرخطر مثل pack size

خروجی فنی:

- اجرای کامل backend و frontend
- database migration سالم
- تست fixtureهای مرجع
- اطمینان از رعایت ساختار `backend/` و `frontend/`

معیار پذیرش:

- fixtureهای V1 و V2 همان summary مرجع را تولید کنند.
- compare بدون login قابل استفاده نباشد.
- session token در JavaScript storage ذخیره نشود.
- تمام تست‌های موجود پاس شوند.

مفاهیم یادگیری:

- Modular Monolith
- FastAPI dependency boundaries
- Next.js App Router
- React Query mutation
- Zod runtime validation
- secure server-managed session

## Sprint 1 — مدیریت تأمین‌کننده

وضعیت: انجام‌شده در 2026-09-02.

هدف:
ساخت موجودیت Supplier برای اینکه هر فایل قیمت به یک تأمین‌کننده مشخص وصل شود.

مشکل کاربر که حل می‌شود:
کاربر فایل‌های قیمت تأمین‌کنندگان مختلف را قاطی نمی‌کند و تغییرات هر تأمین‌کننده جداگانه قابل پیگیری می‌شود.

چرا الان:
کلید تطبیق واقعی محصول `supplier_id + normalized_product_code` است. بدون Supplier، persistence قیمت و versioning معنی دقیق ندارد.

خروجی محصول:

- صفحه لیست تأمین‌کنندگان
- فرم ایجاد تأمین‌کننده
- صفحه جزئیات تأمین‌کننده
- وضعیت فعال/غیرفعال برای تأمین‌کننده

خروجی فنی:

- جدول `suppliers`
- repository tenant-scoped
- endpointهای `GET/POST/PATCH` برای Supplier
- frontend service با `schema/api/hooks`
- تست tenant isolation

معیار پذیرش:

- هر سازمان فقط تأمین‌کننده‌های خودش را ببیند.
- نام تأمین‌کننده در هر سازمان تکراری نباشد.
- حذف سخت انجام نشود؛ برای شروع deactivate کافی است.
- خطاهای تکراری، دسترسی غیرمجاز و داده نامعتبر code پایدار داشته باشند.

مفاهیم یادگیری:

- multi-tenancy در repository
- unique constraint ترکیبی
- CRUD حداقلی بدون overengineering
- طراحی فرم با validation
- React Query query keys و invalidation

## Sprint 2 — ذخیره فایل و Import Draft

هدف:
تبدیل compare موقت به جریان import پایدار؛ فایل قیمت جدید به Supplier وصل شود و نتیجه استخراج در دیتابیس ذخیره شود.

مشکل کاربر که حل می‌شود:
کاربر مجبور نیست هر بار فایل قبلی و جدید را دوباره انتخاب کند. سیستم تاریخچه import دارد و می‌داند هر داده از کدام فایل آمده است.

چرا بعد از Supplier:
هر import باید owner مشخص، organization مشخص و supplier مشخص داشته باشد. بدون آن، داده قیمت orphan و غیرقابل اعتماد می‌شود.

خروجی محصول:

- آپلود فایل قیمت برای یک تأمین‌کننده
- نمایش وضعیت import
- مشاهده ردیف‌های استخراج‌شده قبل از تأیید

خروجی فنی:

- جدول‌های `source_documents`، `import_runs` و `extracted_rows`

- ذخیره metadata فایل، نه مسیر خام کاربر

معیار پذیرش:

- فایل اصلی یا metadata آن به Supplier وصل باشد.

مفاهیم یادگیری:

- persistence design

- idempotency با hash
- application use case
- جداسازی domain از infrastructure

چرا بعد از Import Draft:

خروجی محصول:

خروجی فنی:

## Sprint 4 — نسخه قیمت immutable و مقایسه با آخرین نسخه معتبر

هدف:
ساخت PriceListVersion تا سیستم بداند نسخه معتبر فعلی هر Supplier چیست و import جدید را با آن مقایسه کند.

مشکل کاربر که حل می‌شود:
کاربر به‌جای مقایسه دستی فایل قدیم و جدید، فقط فایل جدید را آپلود می‌کند و سیستم با آخرین نسخه تأییدشده مقایسه می‌کند.

چرا بعد از کیفیت داده:
نسخه معتبر نباید از داده مبهم یا ناقص ساخته شود. اول draft و validation، بعد versioning.

خروجی محصول:

- نمایش آخرین نسخه معتبر قیمت برای هر Supplier
- compare import جدید با latest approved version
- نمایش تغییرات added، removed، price، unit، pack size و metadata
- امکان مشاهده تاریخچه نسخه‌ها

خروجی فنی:

- جدول‌های `price_list_versions` و `price_list_items`
- immutable write model
- queryهای tenant-scoped
- endpoint برای مشاهده version و change report
- frontend pages/hooks برای version history

معیار پذیرش:

- نسخه approved قابل update مستقیم نباشد.
- تغییر pack size و unit جدا و پرخطر نمایش داده شود.
- قیمت‌ها فقط integer IRR باشند.
- import یک سازمان با version سازمان دیگر مقایسه نشود.

مفاهیم یادگیری:

- immutable data modeling
- auditability
- read model vs write model
- طراحی endpointهای versioned
- performance query برای لیست‌های بزرگ

## Sprint 5 — Approval Workflow و Audit Log

هدف:
اضافه‌کردن تأیید انسانی رسمی پیش از اینکه یک فایل قیمت مبنای فروش شود.

مشکل کاربر که حل می‌شود:
فروشنده یا اپراتور نمی‌تواند اشتباهی یک فایل خام، ناقص یا تغییر پرریسک را مبنای فروش کل شرکت کند.

چرا بعد از versioning:
Approval باید روی draft/version مشخص اعمال شود و اثر آن قابل ردیابی باشد.

خروجی محصول:

- وضعیت‌های draft، ready_for_review، approved، rejected
- صفحه review قبل از approval
- دکمه approve/reject با پیام هشدار
- نمایش اینکه چه کسی و چه زمانی نسخه را تأیید کرده است

خروجی فنی:

- جدول `audit_logs`
- state machine ساده برای import/version
- role guard برای approval
- جلوگیری از approval خودکار
- تست race condition حداقلی برای approval هم‌زمان

معیار پذیرش:

- فقط کاربر مجاز بتواند approve کند.
- approved version immutable بماند.
- هر approve/reject audit event داشته باشد.
- هیچ import دارای خطای مسدودکننده approve نشود.

مفاهیم یادگیری:

- state machine
- authorization کاربردی
- transactional consistency
- audit trail
- optimistic/pessimistic concurrency در حد نیاز

## Sprint 8 — ساخت پیش‌فاکتور PDF

هدف:
ساخت پیش‌فاکتور فارسی بر اساس قیمت معتبر و قانون قیمت‌گذاری.

مشکل کاربر که حل می‌شود:
آماده‌کردن پیش‌فاکتور از روی Excel، ماشین حساب و فایل Word زمان‌بر و پرخطاست.

چرا بعد از قواعد قیمت:
پیش‌فاکتور باید از قیمت فروش محاسبه‌شده و قابل توضیح ساخته شود، نه از عدد دستی نامطمئن.

خروجی محصول:

- ساخت پیش‌فاکتور draft
- انتخاب مشتری یا واردکردن اطلاعات مشتری حداقلی
- افزودن کالا با قیمت محاسبه‌شده
- تولید PDF فارسی
- نمایش تاریخ اعتبار پیش‌فاکتور

خروجی فنی:

- مدل‌های `customers`، `quotes` و `quote_items`
- reference به `price_list_version_id`
- تولید PDF با فونت فارسی پروژه
- تست snapshot یا regression برای داده PDF

معیار پذیرش:

- هر quote item بداند از کدام price version آمده است.
- قیمت quote بعد از تغییر قیمت خرید، بی‌صدا update نشود.
- PDF فارسی خوانا و قابل چاپ باشد.
- پیش‌فاکتور draft بدون تأیید یا ارسال خودکار باقی بماند.

مفاهیم یادگیری:

- document generation
- aggregate modeling
- Persian typography in PDF
- immutable reference
- مرزبندی write model پیش‌فاکتور

## Sprint 9 — هشدار قیمت منقضی‌شده و پیگیری پیش‌فاکتور

هدف:
تشخیص quoteهایی که به‌خاطر تغییر قیمت تأمین‌کننده ریسک دارند و یادآوری پیگیری quoteهای بی‌پاسخ.

مشکل کاربر که حل می‌شود:
فروشنده متوجه می‌شود کدام پیش‌فاکتور دیگر با قیمت خرید جدید امن نیست و کدام مشتری نیاز به پیگیری دارد.

چرا بعد از quote:
تا وقتی quote واقعی و version reference وجود ندارد، هشدار stale quote قابل اعتماد نیست.

خروجی محصول:

- وضعیت quote: draft، sent، accepted، rejected، expired
- هشدار وقتی version جدید قیمت روی کالاهای quote اثر بگذارد
- لیست quoteهای بی‌پاسخ
- reminder دستی یا rule-based

خروجی فنی:

- مدل lifecycle پیش‌فاکتور
- query برای quoteهای affected by price change
- notification log داخلی
- بدون ارسال خودکار پیام در شروع

معیار پذیرش:

- سیستم فقط هشدار بدهد؛ ارسال خودکار انجام ندهد.
- stale بودن quote بر اساس version reference محاسبه شود.
- reminderها قابل ردگیری باشند.
- تغییر قیمت خرید، quote قبلی را دستکاری نکند.

مفاهیم یادگیری:

- event-like business logic بدون event bus پیچیده
- scheduled jobs حداقلی
- lifecycle modeling
- risk-based UX
- جداسازی notification suggestion از ارسال واقعی

## Sprint 10 — آمادگی پایلوت پولی Excel

خروجی فنی:

- observability اولیه

- مستندات deploy و runbook

معیار پذیرش:

- حداقل یک تعهد تجاری واقعی ثبت شود.
- مالک بتواند بدون کمک توسعه‌دهنده مسیر اصلی را طی کند.

مفاهیم یادگیری:

- incident basics

## Sprint 11 — پردازش background برای فایل‌های بزرگ

چرا بعد از پایلوت اولیه:

مفاهیم یادگیری:

## Sprint 12 — استخراج PDF متن‌دار

بعضی تأمین‌کننده‌ها لیست قیمت را PDF می‌فرستند و کاربر مجبور است دستی آن را به Excel تبدیل کند.

چرا قبل از تصویر و Vision:
PDF متن‌دار کم‌هزینه‌تر و قابل کنترل‌تر از OCR تصویر است و می‌تواند نیاز بخشی از بازار را زودتر پوشش دهد.

خروجی محصول:
